## 0. What decides the design (read this first)

**The short verdict [J]:** an MCP server is feasible and mostly *reuses* what exists: the accounting engines are pure and run headless unchanged. But the only thing an API key can read today is an unpaginated full-collection dump, the only thing it can write is an unvalidated blind append, the transport is HTTP, and the key is tenant-wide with no expiry or rate limit. So: a **read-only, snapshot-based v0** is buildable with no backend change; **anything that writes, or reads a large book, or is reachable from a hosted AI product, needs named backend seams first** (section 1.7 and 3.7).

1. **The engines are importable headless: 133 of 136 `src/core` modules have a clean import closure.** The three that reach Dexie, the store or localStorage are `core/navPlan.ts` (→ `state/recents.ts`), `core/snippetStore.ts` and `core/undo.ts` (→ `data/db.ts`, `data/writeGuard.ts`, `sync/baseline.ts`); none is an engine an MCP needs [M, section 2.3]. One `esbuild` bundle of 14 engines is 185 KB (46 input files, the synthetic-data generator included) and runs in plain Node [M].
2. **A headless book reproduces the app's own identities.** On the harness's synthetic company the Balance Sheet from `core/splitCompany.ts balanceSheetOf` balances to the paisa at 50k and 250k vouchers (difference 0.00), Data Check runs (`core/integrity.ts checkIntegrity`), and every report engine finishes in 10-500 ms at 250,000 vouchers on this laptop (GSTR-1 + 3B together 1.5 s on a cold first call; the harness's warm figure is 136-142 ms) [M, section 2.6].
3. **Some report logic still lives inside React components** and must be re-created or extracted: the Balance Sheet *tree rows* (`ui/reports.tsx:1693-1768`; the totals and lines are available pure from `balanceSheetOf`), `nextVchNo` / `formatVchNo` (`state/store.ts:719-753`), `partySideOf` (`ui/dash/widgets/compute/common.ts:73-81`), the Bills Receivable / Payable report rows (`ui/reports/outstanding.tsx:70-110`, which still decide a bill's side by sign) and the Day Book's party-name rule (`ui/reports.tsx`, mirrored in `scripts/perf/passes.ts:141-153`). The perf harness already keeps "MIRROR" copies of these with a drift guard (`scripts/perf/mirrors.mjs`); an MCP build should do the same (section 2.5).
4. **The read path an API key has is `GET /v1/:collection`: no limit, no cursor, no `since`, no sort control, no revision in the response** (`backend/src/rest.js:31-44`). It `DISTINCT ON (cid, doc_id)`-sorts *every revision* of the collection. At 250,000 live vouchers (294,141 change-log rows for the tenant) that query took **3.2 s of database time with a disk sort (5.4 s wall including transferring the rows)** on a laptop with Postgres 14, and the answer is about **175 MB of JSON** at the harness's 700 B per voucher, uncompressed (the server registers no compression) [M]. `/sync/pull`, which *is* cursor-paged, cannot be called with an API key (`backend/src/authenticate.js:8-14`).
5. **The write path an API key has is a blind append that validates nothing** (`backend/src/rest.js:58-76`): no balance check, no reference check, no period lock, no number, no `base`, no size cap below the 20 MB body limit (`backend/src/server.js:28`). The design promised validation ("validate (Dr=Cr, refs, period-lock)", `docs/ARCHITECTURE.md:1554`); it was never built. The engines **throw** on a voucher with an unknown `base` or no `entries`, and a string `amount` of `"5"` silently turns a balance into the string `"05"` [M, section 3.1]. One bad API write can make every report on every device throw.
6. **An API write cannot reserve a voucher number.** The server's number reservation (`/sync/next-number`, wave 3, not deployed) authenticates with the Bearer token only (`backend/src/sync.js:319-325`), never an API key, and `POST /v1/vouchers` assigns nothing. Number assignment for an API voucher therefore has to happen client-side (the MCP guessing "highest + 1"), which is exactly the collision the server numbering was built to end (section 3.3).
7. **There is no idempotency and no optimistic concurrency.** `POST /v1/:collection` with no `docId` generates a random UUID (`rest.js:64`): a retry after a timeout posts the voucher twice. With a `docId` it *replaces* the document silently (`rest.js:65-72`) and never consults any base revision, so an AI edit of a voucher a person changed after the AI read it is an unrecorded lost update (the conflict check lives only in `/sync/push`: `backend/src/sync.js:205-293`).
8. **An API key is the whole tenant, forever:** scopes are only `read` / `write` (`backend/src/platform.js:83`), no company scope (`cids`), no expiry, no rate limit (the limiter guards only login and password routes: `backend/src/ratelimit.js`, used in `auth.js`, `admin.js`, `changePassword.js`), no per-request audit (only `last_used_at`, `platform.js:14`), and any signed-in member can mint one (`platform.js:78-90` has no role check although the app's own screen is administrator-only: `src/core/access.ts:164`). The design said otherwise (`docs/ARCHITECTURE.md:1106-1121`: `cids`, `rate_tier`, `expires_at`, "a key can never exceed its creator's rights"); the built `api_key` table has none of it (`backend/sql/006_p4.sql:6-18`). The plan flag `features.api` (`backend/sql/003_saas.sql:56-60`) is read by nothing that gates a request.
9. **The read redaction is incomplete for legacy secrets.** `redactForRead` strips `vault`, `vaultLegacy`, `security` from companies and `pinHash` from users (`restPolicy.js:33-39`, `conflict.js:38-41`) but **not** `Company.vaultPin` (a legacy plaintext passcode, `src/types.ts:130`) or `User.pin` (a legacy plaintext PIN, `types.ts:717`). The app hashes these when a device opens the company (`store.ts` `migrateLegacySecrets`) but the server's latest revision holds whatever the last writer pushed; `core/vault.ts:506-517` says the server history "is out of reach from here". It also hides `Company.security`, which contains `lockedThrough` (the period lock) and `enabled`, so a headless writer cannot even *see* the lock through the API. The repo already has a wider rule, `SECRET_KEY` in `core/splitCompany.ts:192`, which an MCP layer should apply to everything it returns.
10. **REST DELETE leaves a ghost in the list route.** It inserts the delete row with `cid = ''` (`rest.js:85`) but the list groups by `(cid, doc_id)` (`rest.js:39`), so the original row (with the real `cid`) is still the latest of *its* group and is returned as live, while `GET /v1/:collection/:docId` and every device say it is gone. Reproduced on the bench database [M, section 1.4]. An MCP must never trust the list route after any API delete, and should not expose delete at all.
11. **Anything the MCP writes is invisible to the app's audit trail.** The Edit Log reads only the *device's own* outbox (`src/ui/admin/AuditLog.tsx:101`), and a pulled change is applied without an outbox row (`src/data/db.ts:413-438`). API rows carry `device_id = 'api'` and `user_id = NULL` (`rest.js:70`, `006_p4.sql:32`), so even the server cannot say *which key* wrote a row. Webhooks fire only for REST writes (`rest.js:74, 88`), never for edits made in the app (`sync.js` never calls `deliverEvent`), so an MCP cannot use webhooks to learn that a book changed.
12. **The "optional voucher" is a ready-made draft mechanism.** A voucher with `optional: true` is recorded and shown in the Day Book (tagged) and the Optional Register but "never reaches any total" (`core/accounting.ts:9`, `core/voucherCancel.ts:259-260`), and a person turns it into a real voucher with Ctrl+L on the voucher screen (`src/ui/VoucherScreen.tsx:3011`) or the selection-wide Mark Regular (`src/ui/reports/markOptional.ts:75`). [J] AI-created entries should be written as optional drafts a human promotes.
13. **Transport is HTTP only** (`docs/HANDOFF.md:89-91`), and only ports 1306/1036/1038 reach the VM (`HANDOFF.md:56-58`). The MCP authorization spec requires HTTPS for every authorization-server endpoint and non-localhost redirect URI, and forbids passing the MCP client's token through to an upstream API [W]. A claude.ai custom connector is called from Anthropic's cloud and the server must be publicly reachable [W]. So a **hosted** MCP for claude.ai/ChatGPT is blocked on TLS; a **local stdio** MCP (Claude Desktop, Claude Code, Cursor) is not, but it would send the customer's API key and books over plain HTTP until TLS exists.
14. **A fourth data source needs no server at all:** a company *backup file* (`exportCompany`, `src/data/db.ts:443-467`, format tag `tallyweb-backup-v2`) has exactly the table shapes the engines take, and `core/backupMigrate.ts` migrates old files to the current schema (pure: import closure is one file). An offline "read a backup" mode serves desktop-only customers, makes tests deterministic, and lets the whole tool catalogue be built and demonstrated before any backend seam exists [J].

## 1. The read path: REST `/v1`, end to end

### 1.1 The routes (all in `backend/src/rest.js`, registered at `backend/src/server.js:51`)

| Route | Scope | What it does | Lines |
|---|---|---|---|
| `GET /v1/:collection` | read | every current, non-deleted document of the collection for the tenant; optional `?cid=` | `rest.js:31-44` |
| `GET /v1/:collection/:docId` | read | the latest revision of one document by id (404 when absent or latest is a delete); **no `cid` filter** | `rest.js:46-56` |
| `POST /v1/:collection` | write | append a `put`: body is the whole document; `docId`/`id` optional | `rest.js:58-76` |
| `DELETE /v1/:collection/:docId` | write | append a `delete` | `rest.js:78-90` |

Collection names are anything matching `/^[a-zA-Z][a-zA-Z0-9_]{0,40}$/` (`restPolicy.js:16`); reads of an unknown name simply return zero rows. Writable collections are `DATA_TABLES` minus `companies, users, roles, einvoices, customFields` (`restPolicy.js:18-22`, `conflict.js:65-72`): **22 collections**: groups, ledgers, vouchers, units, stockGroups, stockCategories, godowns, stockItems, voucherTypes, costCategories, costCentres, employees, payHeads, tdsNatures, priceLevels, budgets, attendanceTypes, employeeGroups, leads, leadActivities, leaveTypes, leaveApplications. All 27 are readable. The in-app API reference (`src/ui/admin/ApiDocs.tsx:31-47`) documents only these four routes.

### 1.2 Authentication, keys, scopes, limits, audit

- **Two ways in** (`platform.js:19-32`): an `X-API-Key` header, looked up by SHA-256 on the **owner pool** (RLS bypass, scoped by the key's own `tenant_id`, `platform.js:9-16`); or a Bearer JWT, which gets both scopes (`platform.js:27-31`). A revoked or unknown key is 401; a missing scope is 403 (`platform.js:33-35`).
- **Key creation** (`platform.js:81-90`): `ck_` + 24 random bytes in hex; only the SHA-256 and a 10-character prefix are stored; shown once; scopes filtered to `read`/`write`, default `['read']`. The row has `tenant_id`, `name`, `created_by`, `last_used_at`, `revoked` and nothing else (`006_p4.sql:6-18`): **no expiry, no company scope, no rate tier**. `created_by` is stored but never put on a write (`rest.js:70` writes `req.userId`, which the API-key path never sets: `platform.js:24`).
- **Rate limits:** none on `/v1`. `ratelimit.js` is an in-memory exponential back-off used only by `auth.js`, `admin.js`, `changePassword.js`. A leaked read key can pull the whole book as often as it likes; each pull holds a pool connection (pool max 10, `db.js:8`) for seconds (1.6).
- **Audit:** `last_used_at` is updated fire-and-forget (`platform.js:14`). There is no request log table; the Fastify logger (`server.js:25-27`) is the only trace.
- **Entitlement:** reads never check the subscription ("pull still works so data is never stranded", `sync.js:184-185`); writes return **402** when the tenant is not `trialing`/`active`/`past_due` (`rest.js:25-26`, `subscription.js:25-45`). An MCP must turn a 402 into a plain message, not a retry loop.
- **CORS** allows `content-type` and `authorization` headers and `GET, POST, OPTIONS` only (`server.js:32-36`): `X-API-Key` and `DELETE` are not allowed from a browser origin. Irrelevant to a server-side or stdio MCP; relevant to any browser-hosted client.

### 1.3 Tenancy, row-level security, and what `cid` is

- One **tenant** per customer account. Every read goes through `withTenant(tenantId, fn)`: `BEGIN`, then `set_config('app.tenant_id', $1, true)` (transaction-local), then the query as the non-owner role (`backend/src/db.js:20-34`). The policy on `change_log` is `tenant_id = current_setting('app.tenant_id', true)::uuid`, with a `WITH CHECK` of the same (`backend/sql/002_p2.sql:67-69`), default-deny when the GUC is unset. RLS is `ENABLE`, not `FORCE`, and the runtime role is not the owner (`HANDOFF.md:92-93`). [M] On the bench database, as a non-owner role, the same query returned only the setting tenant's 294,141 of 344,141 rows.
- The tenant comes from the key lookup or the JWT `tid`, never from the request (`platform.js:24, 31`; `tenancy.js:14-17` falls back to the user's oldest membership for an old token). Membership rows are only ever created as `owner` at signup (`tenancy.js:10`; no invite code exists), so **today a tenant has exactly one login**.
- **`cid` is the app's company id**, nothing server-side: `Company.id` of a `companies` document (a UUID for a user-created company; the sample company's id starts `sample-`, `src/core/demo.ts:44`). Every other document carries `cid` in its payload; the change-log column `cid` is a copy used for filtering (`db.ts:333`: `cid = table === 'companies' ? doc.id : doc.cid ?? ''`). The SQL `company` table (`002_p2.sql:22-29`) is **never written** (no `INSERT INTO company` anywhere in `backend/src`). Many companies can sit in one tenant: **`?cid=` is the only company selector and it is optional** (`rest.js:37`). Without it the list mixes every company's rows, and feeding that to an engine gives wrong totals. An MCP must always pass `cid`, re-filter on `doc.cid === cid`, and take the company list from `GET /v1/companies`.
- Reserved masters are found by *derived ids*, not by name: `gid(cid, 'sales')` = `${cid}-g-sales`, `vtid(cid, base)` = `${cid}-vt-${base.toLowerCase()}`, `mainGodownId`, `plLedgerId` (`src/data/defaults.ts:41, 74, 87`; `types.ts:1134`). So `cid` must be the real company id for any group-based report to work.

### 1.4 How a "collection" is materialised, soft deletes, ordering, response shape

- **Materialisation** (`rest.js:38-41`): `SELECT DISTINCT ON (cid, doc_id) cid, doc_id, op, payload FROM change_log WHERE tbl=$1 [AND cid=$2] ORDER BY cid, doc_id, seq DESC`, then `op <> 'delete'` is filtered in JavaScript and each row becomes `{ id: doc_id, cid, ...redactForRead(payload) }` (payload fields win over `id`/`cid`). `change_log` is the append-only history of every revision (`001_p1.sql:34-44`, `payload jsonb`); there is no "current state" table.
- **Soft delete:** a `delete` is a row with `op = 'delete'`, `payload NULL`. The list route drops a document whose *latest row in its `(cid, doc_id)` group* is a delete. **Bug [M]:** `DELETE /v1/...` writes its row with `cid = ''` (`rest.js:85`), so it lands in a different `(cid, doc_id)` group from the document and the list still returns the document. On the bench database a voucher present in the list stayed in the list after a REST-shaped delete, while the single-document query answered "delete". Devices *do* delete it (they delete by `docId`). Deletes pushed by the app carry their `cid` (`sync.ts:621-622`) and are fine.
- **Ordering:** `(cid, doc_id)`, i.e. by random UUID. Not by date, not by creation. There is no sort parameter.
- **Response shape:** `{ collection, count, data: [...] }` (`rest.js:42`). No `seq`/revision per document, no head revision, no total beyond `count`, no pagination token, no ETag.
- **Redaction** (`restPolicy.js:33-39`, fields at `conflict.js:38-41`): companies lose `vault`, `vaultLegacy`, `security`; users lose `pinHash`. **Not** redacted (all returned to any read key): `Company.vaultPin`, `User.pin` (legacy plaintext, finding 9), `Company.logo` (a base64 data URL, can be large), and the personal data on masters: `Ledger.bankAcNo`, `bankIfsc`, `gstin`, `pan`, `phone`, `email`, `address` (`types.ts:297-320, 350`), `Employee.aadhaar`, `pan`, `bankAcNo`, `uan`, `salary` (`types.ts:771-789`), `Lead.phone/email`, and the `users` rows' emails.

### 1.5 Pagination, limits, since-cursor: what exists

- **`/v1` list: none** (`rest.js:31-44`): no `limit`, `offset`, `since`, `after`, `fields`. Extra query parameters are ignored.
- **`/sync/pull`** is the cursor-paged feed: `since` (default 0), `device`, pages of **500** (`sync.js:20, 343-374`), capped at the committed high-water mark `MAX(seq)` (`sync.js:352`) so a cursor never skips a row, returning `{ changes, cursor }` where `cursor` is the last `seq` of a full page, else `max(since, MAX(seq))` (`sync.js:370`). It returns *raw change rows* (every revision, including deletes), suppresses the pulling device's own echoes and any revision the device has itself superseded (`sync.js:359-365`). **An API key cannot use it:** the route's preHandler is `app.authenticate`, which verifies a Bearer JWT only (`authenticate.js:8-14`).
- **Could a key-friendly bulk read exist?** Yes, with a small seam (section 1.7). The measured queries it would use are in 1.6.
- A JWT *can* call `/sync/pull`, and the MCP could log in with an e-mail and password. [J] It should not: it would put the customer's password (or a refresh token, 30-day TTL, `config.js:29`) in an AI tool's config, with a login that has every right, no scope and no revocation of just that tool.

### 1.6 What reading a big book costs (measured, with the assumptions stated)

**Dataset [M]:** the perf harness's synthetic company (`scripts/perf/synth.ts`: about 500 ledgers, 300 stock items, mix and shape documented in `docs/PERF.md:100-135`) at 250,000 vouchers, loaded as change-log rows into a scratch Postgres 14.20 on an Apple-silicon laptop: 250,000 vouchers, 35,714 second revisions (every 7th voucher edited once), 7,575 deletes, plus a second tenant of 50,000 vouchers as RLS noise; 344,141 rows, **393 MB** table plus indexes; default `work_mem` 4 MB. The migrations `001`-`008` were applied unchanged. The VM runs Postgres 16 on unknown hardware: trust the *ratios*, not the milliseconds.

**Payload size [M]:** compact JSON is **695 B per voucher at 2k and 702 B at 50k** (gzip 83-86 B, about 8x); a ledger is 243 B, a stock item 346 B. So 250k vouchers ≈ **175 MB raw, about 21 MB gzipped** (linear extrapolation). The server does not compress (no compress plugin in `server.js` or `backend/package.json`). [J] Real documents are larger than the synthetic ones (GST snapshots on every line, bill allocations, dispatch/e-way, narrations); assume 1-2 KB each for planning, which puts 250k vouchers at 250-500 MB. The V8 maximum string length is 536,870,888 characters (`require('buffer').constants.MAX_STRING_LENGTH` on the local Node 25 [M]; the VM runs Node 22, same engine family but **[unverified]** for that exact build), so a single `JSON.stringify` of the list response can fail with "Invalid string length" somewhere past roughly 350,000-750,000 vouchers depending on document size [J].

| Operation (tenant with 250,000 vouchers) | DB time [M] | Notes |
|---|---|---|
| `GET /v1/vouchers` SQL, default `work_mem` | **3.18 s** (EXPLAIN ANALYZE) / **5.37 s** wall incl. row transfer | parallel seq scan + external merge sort, ~88 MB per worker x 3 (`DISTINCT ON ... ORDER BY cid, doc_id, seq DESC` cannot use `idx_change_doc`, whose order is `(tenant, tbl, doc_id, seq)`: `007_sync_conflicts.sql:54`) |
| same, `work_mem = 256 MB` | 1.02 s wall | in-memory sort; the server does not set it |
| anti-join "latest per document" variant | 2.38 s | still a full scan of the table's rows for the collection |
| date-window filter after `DISTINCT ON` | 2.42 s | no index on `payload->>'date'` |
| keyset page of 1,000 documents by `doc_id` (`DISTINCT ON (doc_id)` over `idx_change_doc`) | **3.3 ms** | 250 pages ≈ 0.9 s total; this is the shape a paged route should use |
| seq-ordered page of 1,000 vouchers (`seq > $1 ORDER BY seq LIMIT 1000`) | **0.43 ms** | primary-key scan with a filter |
| one `/sync/pull` page (500 rows) | 18.6-21 ms | 589 pages for 294,141 rows ≈ **11-12 s DB time** plus 589 HTTP round trips |
| `MAX(seq)` for the tenant | 16 ms | the cheap "has anything changed" probe |
| one document by id; the 500-ledger list | 0.5 ms; 1.0 ms | masters are cheap |

**Server-side memory and time for the list route** [J from M and from `docs/PERF.md:112`: 277 MB heap for 250k vouchers as objects]: the `pg` driver parses every payload into objects (about 0.55 s of `JSON.parse` per 250k [M: 111 ms per 50k]), `.filter().map()` with `{...}` spread copies them (second copy), and Fastify then stringifies (about 0.4 s [M: 80 ms per 50k]): transient memory is plausibly **0.8-1 GB per request** and the connection is held for the whole time. Two or three concurrent pulls on a small VM is an outage, and there is no rate limit.

**Over the wire** [J, arithmetic]: 175 MB at 100 Mbit/s is 14 s, at 20 Mbit/s 70 s; gzip would make it 1.7 s / 8 s. The MCP host then parses ≈ 0.55 s and holds ≈ 280 MB.

**What a real customer looks like** [unverified]: no tenant data is available here. A small trader with 5,000-30,000 vouchers a year is 3.5-21 MB raw at 700 B (7-60 MB at 1-2 KB): fine for a one-shot list. The cliff is a multi-year or high-volume book, which is exactly the customer who most wants "ask questions of my data".

### 1.7 Seams the read path needs (none made; all need owner approval; each is small)

| # | Where | Change | Why |
|---|---|---|---|
| R1 | `backend/src/rest.js` list route | `?after=<docId>&limit=N` keyset paging (the 3.3 ms query) and `_seq` on every document (`max(seq)` of its revisions) | bounded memory and time; a revision the caller can later send as `base` |
| R2 | new `GET /v1/head?cid=` | `{ seq: MAX(seq) }` (16 ms) | cache validation: "has anything changed since my snapshot?" |
| R3 | new `GET /v1/changes?since=&limit=&cid=` | the `/sync/pull` query without device echo-suppression, `v1Auth` + read scope | incremental refresh of a snapshot by seq (0.4-20 ms a page) |
| R4 | `rest.js` list/get | an optional `fields` projection and server-side `gzip` | the same pull shrinks 8x |
| R5 | `restPolicy.js redactForRead` | strip `vaultPin`, `pin` and anything matching `SECRET_KEY` (`core/splitCompany.ts:192`) | finding 9 |
| R6 | `rest.js:85` | write the delete row with the document's real `cid` (read it first) | finding 10 |
| R7 | `change_log` | `(tenant_id, tbl, cid, doc_id, seq)` or a `(tenant_id, tbl, seq)` index | lets the `?cid=` list avoid the sort |

Until R1-R3 exist, the MCP must treat a snapshot as expensive (one pull per company per refresh, TTL-cached, refreshed on request, and refusing outright above a document-count guard), and must say "books as of <time>" in every answer.

### 2.4 How the app builds its working arrays, and the headless equivalent

`store.ts loadInto(cid)` (`:306-362`) is the whole recipe. A headless loader must do the same, **without** the writes:

1. **Fetch every table for the company** (`db.ts loadCompanyData`, `:567-608`, 26 tables) and keep only `doc.cid === cid`. Over REST that is 26 calls with `?cid=` plus `GET /v1/companies/<cid>` (the company doc has no `cid` filter issue: its `id` is the `cid`).
2. **Quarantine malformed documents before any engine sees them** (section 3.1: an unknown `base`, missing `entries`, or a non-number `amount` breaks or corrupts every total). Report them in the answer; do not throw.
3. **Seal and sort the vouchers exactly as the store does:** `vouchers.map(sealCancelled).sort((a, b) => a.date === b.date ? a.number - b.number : a.date < b.date ? -1 : 1)` (`store.ts:294-295`, mirrored at `scripts/perf/passes.ts:200-201`). `sealCancelled` matters: the GST/stock/pending-order engines test `v.optional` directly, not `postsToLedgers`, and a half-cancelled voucher an older client wrote reads as live without it (`voucherCancel.ts:216-238`). **Tie order matters** for stock valuation: `stockMovements` orders same-date movements by *array position* (`inventory.ts:33-48`), and the app's array order for same-date, same-number vouchers (a Sales 5 and a Receipt 5 on one date) is IndexedDB primary-key order, i.e. by `id` in UTF-16 code-unit order (`scripts/perf/passes.ts:219-222`: "Dexie hands vouchers back in primary-key order"). So sort by `id` first (a stable sort then keeps that order for ties) or FIFO/average-cost values can differ from the app's [J].
4. **Do not run the lazy seeds, but know they exist** (`store.ts:321-350`): reserved voucher types missing from an old company, the TCS natures, the TDS seed migration, attendance types are *written* on open. A tenant whose devices never opened the company since a type was added has none of them in `change_log`: add `defaultVoucherTypes(cid)` entries to the in-memory arrays for any `vtid(cid, base)` that is missing, and write nothing.
5. **Period:** `from = company.finYearFrom`, `to = addDays(addYears(from, 1), -1)` (`store.ts:351-352`; `dashPeriod.finYearOf`, `:23`). The app's report period is per open company; an MCP takes `from`/`to` per call and defaults to the financial year. April is hard-wired as the financial-year start month in `fyStartFor` and valuation (`dates.ts:50`, `inventory.ts:92`).
6. **"Today"** is `toISO(new Date())` in the *machine's* time zone (`core/dates.ts:4-13` use local getters). An MCP process on a UTC host would age bills against the wrong date for part of every Indian day: compute today in `Asia/Kolkata` and pass it into `ageingAsOn`/`buildDashIndex`; set `TZ=Asia/Kolkata` for the process [J].
7. **The guards every total must respect** (a new report that skips one breaks books-vs-report reconciliation, `CLAUDE.md` "optional vouchers"): ledger balances count only `postsToLedgers(v)` = `baseInfo(v.base).accounting && !v.optional && !v.cancelled` (`accounting.ts:9`: Memorandum, orders, delivery/receipt notes, stock journals, physical stock, attendance post nothing; post-dated vouchers post by their date); stock moves skip `v.optional` and orders/notes with `stock: 'none'` (`inventory.ts:26-31, 39`) and resolve Physical Stock lines as a delta against the running per-godown balance (`inventory.ts:113-125`); GST builders skip `v.optional` (`gstr1.ts:427, 524, 570, 822`, `gstr3b.ts:225`); the party's side is its *group*, never the sign (`common.ts:66-72`); a voucher's headline amount is its party leg (`voucherHeadlineAmount`, `accounting.ts:130-151`); never age a bill into the future (`ageingAsOn`); opening balances always count in a balance and never in a movement.
8. **Names:** ids are opaque. Resolve names after the engine call from `ledgersById`; an entry whose ledger no longer exists is skipped by `dashIndex` and creates a stray map key in `closingBalances` (`accounting.ts:21-23`).

## 3. The write path

### 3.1 What `POST /v1/:collection` does and does not do

Does (`rest.js:58-76`): checks the collection name, the key's write scope, that the tenant may write cloud data (not expired or canceled, `rest.js:21-28`), and that the collection is in the writable 22 (`restPolicy.js:22`); takes `cid = String(body.cid || '')`, `docId = body.docId || body.id || randomUUID()`, builds `payload = {...body, id: docId, cid}` (the `cid` key only if non-empty, line 68), inserts one `change_log` row (`device_id 'api'`, `user_id` NULL, `ts = Date.now()`) under the tenant's advisory lock (so `seq` order is commit order: `db.js:36-52`), then nudges the tenant's SSE clients (`rest.js:73`) and fires the `<collection>.created` webhook (`rest.js:74`). Returns `201 { id, cid, seq }`.

Does **not**: validate any field; check the `cid` exists or belongs to the tenant (any string is accepted; **a document written without `cid` has `payload.cid` unset and no device will ever show it in a company**); check referenced masters; check Dr = Cr; check the period lock or operator rights (those are client-side: `data/writeGuard.ts`, `db.ts:334`); assign a number; consult a base revision; run the conflict check; cap size below 20 MB; refuse an overwrite of an existing id; apply `checkDelete` referential integrity (which is `store.ts:797`-onward, client-only) or the e-invoice delete guard (`store.ts:711`); post the reverse-charge Journal (`rcmAfterSave`, `store.ts:703-704`), TDS/TCS assist, credit-limit, negative-stock or duplicate-supplier-invoice checks (all voucher-screen code).

**Hostile-input probes [M]** (the real `accounting.ts`/`inventory.ts`, run through `esbuild`): a voucher with `base: 'Foo'` makes `closingBalances` throw `Cannot read properties of undefined (reading 'accounting')` (`postsToLedgers` calls `baseInfo(v.base).accounting`, `accounting.ts:9`, and `baseInfo` is `VCH_BASES.find(...)!`, `types.ts:47`); a voucher with no `entries` throws `v.entries is not iterable`; `stockPositions` throws on the same unknown `base` (`inventory.ts:27-28`); an `amount` of the string `"5"` does not throw, it makes the ledger balance the string `"05"` by concatenation; an entry to an unknown ledger is silently tolerated. The app applies pulled documents without validating them (`db.ts:413-438`), so **one malformed API document stops every report on every device**, and the API's only protection is whatever the MCP does first.

### 3.2 What a valid voucher document must contain

Reading `types.ts:991-1049`, `core/demo.ts:348-394` (a complete sales/purchase invoice builder), `core/integrity.ts:409-428` and the engines, a document the app will accept as a normal voucher is [J, synthesised from those, with the controlling lines cited]:

- `id` (string, unique; **deterministic** for idempotency, 3.3), `cid` (an existing company), `typeId` (an existing `VoucherType.id` of that company; the reserved ones are `vtid(cid, base)`), `base` (one of the 17 in `VCH_BASES`, `types.ts:26-45`), `number` (integer ≥ 1), `numberStr` (non-empty; the formatted number), `date` (ISO `YYYY-MM-DD`), `narration` (string, may be empty).
- `entries[]`: each `{ ledgerId, type: 'Dr'|'Cr', amount }` with `ledgerId` an existing ledger of the company, `amount` a finite **number**, and **total Dr = total Cr to the paisa** (`checkIntegrity` compares in whole paise, `integrity.ts:411-417`). Payment, Receipt, Contra, Journal vouchers are just entries; a bank leg may carry `instrument`, `instrumentDate`, `instrumentType`.
- Invoices (Sales, Purchase, Credit Note, Debit Note): `partyId` (a ledger under Sundry Debtors/Creditors), `itemLedgerId` (the sales or purchase ledger), a party entry on the party's side, an entry per GST head on the matching tax ledger (found by `Ledger.taxType`), optionally a `Round Off` ledger entry (found by name; `ensureLedger('Round Off', 'indirectexp')`, `store.ts:756-769`), `inventory[]` lines `{ stockItemId, godownId, qty, rate, amount }` **with the GST snapshot** `gstRate`, `taxability`, `hsn`, `cessRate` taken from the item as on the voucher date (`demo.ts:358-366`; without it a later change to the item re-taxes the invoice: `types.ts:956-966`), bill allocations on a bill-wise party (`entries[].bills = [{type:'New Ref', name: numberStr, amount, dueDate}]`, `demo.ts:379-382`), `placeOfSupply` when it differs from the party's state, `supplierInvNo`/`supplierInvDate` on a purchase. GST amounts come from `computeItemGst(lines, itemsById, isIntraState(company, party, placeOfSupply), date)` (`core/gst.ts:93-108, 9-24`).
- Never set by a writer: `cancelled`, `irn`, `ackNo`, `ewb`, `numberLog`; `numberStatus` only as `'provisional'` for a number not yet confirmed.
- A draft: `optional: true` (finding 12).

**Validators that already exist and are pure** (the MCP should run them before any write): `checkIntegrity` on `books + the new voucher` (it reports `unbalanced`, `missing-master`, `duplicate-number`, `integrity.ts:407-470`) and `writeDenial(ctx, {table, op, id, doc})` (`core/access.ts:351-369`; period lock `lockedThrough` at `:269-271`, role dates, voucher bases). Neither rejects an unknown `base` or a non-numeric amount for a *non-accounting* base (`integrity.ts:410` uses `baseInfo(v.base)?.accounting`), so the MCP needs its own shape validator first. The period lock note: `writeDenial` exempts `full`-rights operators (`access.ts:355`), and an MCP is not an operator. [J] It should treat `lockedThrough` as binding on itself, always; but over REST the company's `security` field is stripped (finding 9), so the lock is invisible to an API-key writer today.

### 3.3 Voucher numbers: client-side versus the server's reservation

- **The app's rule** (`store.ts:719-735`): `max(number of this type's vouchers in the numbering window of the date, carriedNumber(vt, date), burnedNumber(einvoices, vt, date)) + 1`, where the window is the financial year (`restart: 'Yearly'`), the month (`'Monthly'`) or none (`core/voucherNumberFloor.ts:20-31`), `carriedNumber` is a split company's carried floor, and `burnedNumber` keeps a number the e-invoice portal has been given (`einvoiceState.ts:310-322`). `numberStr` = prefix + zero-padded number + suffix with `{fy}` `{yy}` `{yyyy}` `{mm}` tokens (`store.ts:737-753`). A `Manual` type is the person's own number (`VoucherType.numbering`, `types.ts:536`).
- **The server's rule** (wave 3, **uncommitted, not deployed**): one counter per series *(tenant, company, voucher type, window)* in `voucher_series`, and a ledger of issued numbers in `voucher_number_issue` whose primary key is the number itself, `UNIQUE (tenant_id, key)` for idempotency (`backend/sql/008_voucher_series.sql:18-39`). `POST /sync/next-number {cid, typeId, window, floor, key, voucherId}` answers `max(counter, floor, 1)`, replays on the same `key`, never lowers, never reissues (`backend/src/numbering.js:119-128, 203-218`); `claim` (a number a device issued offline) and `release` follow (`:221-249`). The client half is `core/vchNumbering.ts` (`reserveBody` `:116-119`, `numberKey` `:74-77`, `seriesOf` `:54-56`), pure and reusable.
- **The gap:** `/sync/next-number`, `claim` and `release` are registered with `app.authenticate` (Bearer JWT) (`sync.js:319-325`), **not `v1Auth`**, so an API key cannot call them, and `POST /v1/vouchers` neither reserves nor ledgers a number. An API voucher numbered by the MCP's own "highest + 1" is invisible to `voucher_series`; the next device reservation uses `floor` = its *own* local next number, which counts the API voucher only once that device has pulled it. Two paths to a **duplicate GST invoice number**: (a) the MCP and a device number concurrently; (b) the API voucher arrives after the device took the number. The app records such a clash on arrival (`sync.ts:659-678` `checkDuplicates`, 5,000-arrival cap) in the Sync Mismatch Report, but it never renumbers automatically (`vchNumbering.ts:7-14`).
- **Needed (seam W2):** let `reserve` accept an API key, or add `POST /v1/vouchers/number` with the same body, so the MCP calls `reserveBody(...)` (`floor` = its snapshot's local next number, `key` = the voucher id) and writes the returned number; then write the voucher with `numberStatus` unset (a confirmed number). `NUMBER_LIMITS` caps a number at 999,999,999 and a tenant at 20,000 series (`numbering.js:33-40`). Until then MCP-created vouchers should be limited to types where the person types their own number (`Manual`), or be refused.

### 3.4 Revisions, baselines, conflicts: what an API write has to state

- The app stamps every change-log row with the **base**: the highest server `seq` it had applied (`src/sync/baseline.ts:46-53`) and `/sync/push` sends it (`sync.ts:625`). The server compares it with other devices' later revisions of the same document and, on a stale write, **accepts it, records both versions** in `sync_conflict`, and keeps the passcode/PIN fields from the newer revision (`conflict.js:177-232`; `sync.js:205-293`).
- **`POST /v1/...` states nothing and is checked against nothing** (`rest.js:69-72`; the conflict path is only in `/sync/push`). Consequences: (1) an MCP "edit voucher" is a read-modify-write with no precondition: a person's later edit is overwritten and *no mismatch is recorded*; (2) a later stale write from a device over an API revision **is** recorded normally, because `device_id = 'api'` differs from the pushing device (`conflict.js:182`); (3) `companies` and `users` cannot be written through the API at all (`restPolicy.js:18`), so the protected-field rules never matter for it.
- **Needed for any alter/edit tool (seam W3):** `POST /v1/:collection` accepts `base` (the `_seq` a caller read, R1) and answers **409 with the newer revision** when the document has a newer row, using the same query as `loadHistories` (`sync.js:66-106`). **v1 should have no alter tool.**
- **Idempotency:** with a caller-supplied `docId` a repeated identical POST replaces the document with itself (state-idempotent) but still appends a row, nudges devices and fires another webhook (dedupe is by `(endpoint, event, seq)`, and `seq` differs: `platform.js:43-46`). Without `docId` a retry creates a *second voucher*. The MCP must always send a deterministic `docId` derived from its own idempotency key (for example a UUID from a hash of tenant, cid and the tool call's key) and the same `key` for the number reservation.

### 3.5 Stamps, and what an API-created voucher looks like to the app when it syncs down

- **Stamps:** the app's outbox row carries `user` (the sync e-mail), `operator` (the signed-in operator, local only: "the cloud change log records the sync account, not which person at the keyboard", `db.ts:52-55`), `base`, `bk`, `restore`, `origin` (`db.ts:43-69`). The server row has `user_id` (JWT `sub`), `device_id`, `cid`, `ts` (`001_p1.sql`, `sync.js:228-230`). An API row has `user_id NULL`, `device_id 'api'` (`rest.js:70`), and `'api'` is never registered in `sync_device`, so the Sync Mismatch Report shows no device label for it (`sync.js:410-413`). **Nothing identifies the key.** (Seam W4: write `device_id = 'api:<key id>'`, which `DEVICE_ID` allows, `conflict.js:80`, and `user_id = created_by`.)
- **On a device:** the row arrives in `/sync/pull` as `{table:'vouchers', op:'put', payload, deviceId:'api', userId:null}`; `applyRemoteGuarded` puts the payload into Dexie unless that device has an *unsent* edit of the same document (then it is held and recorded as a mismatch, `db.ts:413-438`); `reloadActive` runs `sortVouchers`; `checkDuplicates` runs on arrivals (`sync.ts:659-678`). It appears in registers, the Day Book (tagged Optional if a draft), the Optional Register and every report that its flags allow. It is **not** in the Edit Log (that reads the local outbox only, `AuditLog.tsx:101`), **not** undoable, **not** counted in "Today", and none of the voucher screen's guards ran (3.1). Only the server's `change_log` remembers who wrote it, and only as `api`.
- **Provenance in the document:** `Voucher` has no `source` field. The two options are a narration prefix such as `[AI draft via MCP, key ck_ab12, <date>]` (visible, survives every export; costs nothing) or a new optional field (a `types.ts` seam; `scripts/assert/master-resave.assert.ts` classifies every `types.ts` key and fails on an unknown one, `CLAUDE.md` Phase 24 GOTCHAs). [J] Start with the narration prefix.

### 3.6 Guards that live only in the client (an API write skips all of them)

Operator rights and the period lock (`writeGuard.checkWrite`, `db.ts:334`); referential integrity on delete (`store.ts:797-870`); the e-invoice delete block (`store.ts:707-717`); Dr = Cr and every voucher-screen validation (`VoucherScreen.tsx`); credit limit (`core/creditLimit.ts`); negative stock/cash and duplicate number warnings; TDS/TCS assist; the RCM Journal (`data/rcmWrite.ts`); company passcode (it locks the UI only: `COMSKY_BOOKS_PRODUCT.md:483` "the passcode only locks the screen", "operator rights are client-side"). **An API key outranks every access control the app presents.**

### 3.7 Recommended write design (draft-only first)

1. **v0 and v1: no writes.** A read-only server has no entry in findings 5-8 and 11.
2. **v2, drafts only:** the MCP builds a voucher, runs its shape validator, `checkIntegrity` on a book that includes it, and `writeDenial` against the company's lock, then writes it **`optional: true`** with a narration prefix and a deterministic id. The tool result tells the person where to review it (the Optional Register) and that "Mark Regular" (Ctrl+L on the voucher, or the selection-wide Mark Regular) makes it count. Types: Receipt, Payment, Journal, Contra first (entries only: no GST, no stock, no bills); invoices later, using `computeItemGst`.
3. **Needs before v2 ships:** W2 (number reservation by key), W1 (a validating `POST /v1/vouchers`, or a server-side port of the shape validator: the design's own line `docs/ARCHITECTURE.md:1554`), W4 (attribution), TLS, a per-key rate limit and an optional `expires_at`/`cids` on keys (S-list in section 5).
4. **Never in v1-v2:** alter, cancel, delete, anything on `companies`, `users`, `roles`, `einvoices`, payroll or bank details; creating masters is v3 and needs duplicate-name checks (`integrity.ts:430-449`).
5. Every write tool's description should say it creates a draft, and the client should be left to ask the person (the MCP spec says there should be "a human in the loop with the ability to deny tool invocations" for tools [W]).

## Appendix C. External sources (web research; paraphrased; one short quote at most per source)

- **MCP, transports (revision 2026-07-28) [W]:** https://modelcontextprotocol.io/specification/latest/basic/transports and https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http : two standard transports, stdio and Streamable HTTP (a single POST endpoint; the GET stream and protocol-level sessions were removed in this revision); servers must validate `Origin`, should bind to localhost when local, and should authenticate.
- **MCP, authorization [W]:** https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization and `.../authorization/security-considerations` : optional; HTTP transports should follow OAuth 2.1 with Protected Resource Metadata and the `resource` parameter; **stdio servers should not follow it and take credentials from the environment**; tokens must be audience-bound; a server must not pass the client's token through to an upstream API; every authorization endpoint must be HTTPS and redirect URIs must be `localhost` or HTTPS.
- **MCP, tools [W]:** https://modelcontextprotocol.io/specification/2026-07-28/server/tools : `structuredContent` and `outputSchema`; `isError` results for execution errors; a server must validate inputs, apply access controls, rate-limit and sanitise outputs; clients should confirm sensitive operations. Annotation fields and defaults (`readOnlyHint` false, `destructiveHint` true, `idempotentHint` false, `openWorldHint` true), all hints and never to be trusted from an untrusted server: https://modelcontextprotocol.io/specification/2026-07-28/schema (ToolAnnotations).
- **Claude Code, MCP [W]:** https://code.claude.com/docs/en/mcp : HTTP is the recommended remote transport, stdio for local; a static `--header "X-API-Key: ..."` or bearer header is supported for remote servers; OAuth via `/mcp`; output warning at 10,000 tokens, default cap 25,000 (`MAX_MCP_OUTPUT_TOKENS`), results over 50,000 characters saved to a file unless the tool raises `anthropic/maxResultSizeChars` (up to 500,000). The page was read to character 100,000 of about 123,000; whether it describes annotations in the unread tail is unverified.
- **Claude custom connectors [W]:** https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp : a remote server must be publicly reachable because Anthropic's cloud connects to it (a private server must allowlist Anthropic's published IP ranges); OAuth, or a fixed credential sent as request headers. The page does not state an HTTPS requirement, transports or OAuth versions. A search summary [Ws] says connectors cover Free to Enterprise plans, beta, and that Claude Desktop reads remote servers from Settings > Connectors, not from its JSON config; not confirmed on a primary page.
- **Not researched:** ChatGPT's MCP connector requirements, Cursor's, and any Indian data-protection or accounting-record law as it applies to sending books to an AI provider. These need counsel and the owner's decision; nothing in this file is legal advice [unverified].
