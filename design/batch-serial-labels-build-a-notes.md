# Batch, serial and labels: build notes for the pure engine slices (T-0a, T-5a, T-6a, T-6b)

Written 2026-10-24 in the worktree `/Users/Akshay/tallyreplica/.wt-bs`, branch `trk-batch-serial`, cut from `main` at `432f267` (the commit that holds the reviewed spec).
Source of truth for what was meant: `docs/design/batch-serial-labels-spec.md` (read its section 15.2 for the slices, 15.3 for the order, Appendix R for the stock-key hand-off to the custom-fields lane).
This file says what was built, what was changed by the review, what deviates from the spec, what is NOT built, and how this branch merges. It edits no other document (not CLAUDE.md, `docs/parity-data.json`, `docs/HANDOFF.md` or `COMSKY_BOOKS_PRODUCT.md`).

**Status in one paragraph.** Four slices of pure, new files are built, reviewed once, fixed, and gated: T-0a (the unit, batch, cell and rules engines), T-5a (the scan detector, resolver, scale and GS1 reader), T-6a (the barcode encoders and check digits) and T-6b (the label model, layout, rules, templates and the raw-job emitter). Nothing in the running app imports any of it, so no screen, key or number a user can see has changed (asserted by the full existing suites: 97 of the 101 existing suites report identical counts to `main`; the other four are scanners that run one check per `src` file and so gained assertions only because 28 `src` files were added). Everything is BETA in the plain sense: proved in Node (and, for barcodes, against recorded verdicts of independent decoders on macOS), never run in a browser, never run against a real scanner or printer, never run against a real Postgres.

## 2. What was built, slice by slice

All counts below are the final gate's (after the review fixes). "Mutations" are the deliberate source mutations each suite's list applies; every one must make its suite fail.

### T-0a: the pure model and engines (lane M; all new files)

**Files.** `src/trackTypes.ts` (the types, in a new file; `types.ts` is not edited); `src/core/unitId.ts` (identifier normalisation, IMEI/Luhn re-exported from `backend/src/unitKey.js`); `backend/src/unitChain.js` with `.d.ts` and `backend/src/unitKey.js` with `.d.ts` (the chain engine, shared by client and server; `src/core/unitChain.ts` re-exports it: events, `orderUnitEvents` (rule W), chains by `uid`, `pendingSlots` and adoption, `violations`, `patchVoucher`, `unitCostLedger`); `src/core/batches.ts`; `src/core/trackRules.ts` (rules R1 to R31 as one function with four callers); `src/core/stockCell.ts` (length-prefixed cell keys, algebra, `countSpread`, projections, `movementCellEffects`, `patchCells`); `scripts/fixtures/trackingBook.ts` (the generator of valid books); `scripts/assert/support/trackKit.ts`.

**Suites (assertions / mutations killed).** `unitid` 301 / 64, `trackunit` 265 / 112, `trackbatch` 183 / 116, `trackrules` 427 / 301, `trackcell` 194 / 86, `trackledger` 85 / 50, `trackprops` 672 / 46 (the cross-module property suite added in this resume), `trackindex` 37 / 20 (added by the fix pass). Total 2,164 assertions, 795 mutations. They cover the rule W vectors the spec names (same-day sale and return numbered either way, purchase above a same-day sale, sell-return-resell, a return from a party never sold to), the adoption, supersession and transfer vectors, hostile inputs (10,000-serial pastes, Unicode digits, malformed ids) and CF's five stock vectors with batch and batch-plus-variant keys including hostile batch names.

**Deviations from the spec text (all deliberate, all asserted).**
1. `normaliseUnitId` REFUSES a raw text over 64 characters (spec 3.3 step 1 says "cut it"): a stored 64-character prefix of a pasted line would be an identifier nobody typed. The cap still comes before any pattern test.
2. `parseExpiry` does not accept the entry-field date mnemonics (spec 3.4 says "and the existing mnemonics"): Phase 20's gotcha, mnemonics are opt-in, a mis-mapped column holding `R` must not become the year end.
3. Rule W's `validNext` adds a GODOWN test to the spec's two tests, so a same-day sale, return and restock is told apart from a real wrong-godown sale.
4. Names differ from the spec's module map: `buildUnitModel` for `buildChains`, `dependantsOf` for `dependants`, `foldBatches` takes a `cellsOf` callback. Helpers added that the map does not name: `safeVoucher`, `linesOf`, `MAX_QTY`, `MAX_RUPEES`, `unitUnrecorded`, `dataCheckTracking`.
5. A Stock Journal line with every unit identified yields no `moveIn`/`moveOut` of n = 0 (no-op contributions are dropped; behaviour unchanged, asserted).
6. The paste-header vocabulary is wider than the spec's (Sr, Sl, colour, storage, grade, lot, date, price and similar); a first line made only of such words is skipped and reported. Judgement, recorded in the code.
7. The `since <= d` filter of an adoption is redundant (the sweep runs date by date); kept as a guard, documented as an equivalent mutant. Other guards that were unkillable were removed instead (R27's base list, `delete fin.line` on R7, `tables.has` in `cellRules`, `inBooks(draft)` before the cell entries).
8. Timing assertions use CPU time with generous bounds (they guard only against quadratic blow-ups). The spec's budgets (`trk.units`, `trk.accept`, the 150 ms paste) are perf rows for T-0b, not asserted here.

**Known limit, documented in `arrangeChain`.** An unidentified unit that is sold at one godown, returned into another and moved by a Stock Journal, all on one date, can be arranged with the move first and reported `notInStock`; the wildcard cannot tell which godown the adoption slot was at. R3 is overridable and an explicit purchase `in` ends the wildcard. The valid-book generator avoids that day. A slot-aware search would fix it.

### T-5a: the pure scan half (lane S + M; all new files)

**Files.** `src/core/scanInput.ts` (the timestamp-clocked detector, Caps Lock derivation, the 300 ms backstop rules, the bare-key context test), `src/core/scanResolve.ts`, `src/core/scale.ts` (embedded-price/weight labels), `src/core/scanDevice.ts` (setup-scan analysis, per-connection profiles), `src/core/barcode/gs1.ts` (the GS1 reader, shared with T-6a), `scripts/assert/support/scanHarness.ts`.

**Suites (assertions / mutations killed).** `scaninput` 500 / 108, `scanresolve` 192 / 63, `scale` 156 / 25, `scandevice` 174 / 58, `scanburst` 541 / 46, `gs1` 283 / 40. Total 1,846 assertions, 340 mutations. Hostile bursts, irregular timing traces, scanner bursts at 3 ms spacing with 13 and 15 characters, a main thread blocked for 66 ms inside every keydown (the detector still sees 3 ms gaps because it is clocked by the event's own timestamp).

**Deviations and judgement calls.**
1. The spec's three gap rules cannot all hold, so: a run continues while a gap is at most 3 x `gapMs` and qualifies when at least 90 percent of its gaps (nearest rank) are at most `gapMs`. After the review the rule is read over the whole run, the first gap included (no head key is trimmed).
2. Spec 14.4 step 1 (an IMEI-shaped code that passes Luhn is a candidate for the unit lookup) is an `imeiCandidate` annotation on the unknown outcome, set only after every exact lookup has missed, so a registered 15-digit item code never loses to a one-in-ten Luhn coincidence.
3. An item code with several live batches or MRPs opens a picker (spec 14.4); the resolver reports the ITEM only, because it holds no stock. The entry screen (T-2a) opens the batch picker.
4. Missing GS1 group separator: refused only when the same text has a second complete valid reading as pack-label elements (marked [J] in the code). A batch that really contains a valid AI such as `21` plus data is refused too unless the setup scan proved the scanner sends the separator (`gsKnown`).
5. Bare-key context: the hold decides a burst after 2 keys inside the gap window. A burst cut short of `minLen` is discarded (spec 14.6), not replayed, so a very fast two-key human rollover in a menu on a device that turned the layer on is swallowed.
6. NOT implemented: the GS1 price check digit (General Specifications 7.9) and the 2051+ sliding century. The century is 20YY and day 00 is the last day of the month, both marked [J]; `valueCheckAt` is this build's own simpler mod-10 option.
7. Beyond the spec text: a code over 128 characters (and a PLU over 40) is not registrable and is listed in `BarcodeIndex.skipped` (capped at 200, `skippedMore` counts the rest) instead of being cut. This came from a real defect: the resolver cut every key to 128 characters, so a pack URL that differed from a registered code only after character 128 resolved to the wrong item.

### T-6a: encoders and check digits (lane M; all new files)

**Files.** `src/core/barcode/{check,ean,code128,code39,itf,gs1build,mint,qrsym,render,types}.ts`; `scripts/assert/barcode*.assert.ts`, `barcode.oracle.swift` and `barcode.oracle.mjs` (the independent decoder harness: macOS Vision and CoreImage), `barcode.record.mjs`, and the recorded verdicts as DATA (`barcode.record.json` for Apple, `barcode.bwip.json` for bwip-js; bwip-js is not a dependency and is never imported); `scripts/assert/support/{barcodeCorpus,barcodeOracleEntry,barcodeOracleJob,barcodeRead,qrRead,png,crashGuard,fontMetrics,labelKit,labelOracleEntry}.ts`.

**What it encodes.** EAN-13, EAN-8, UPC-A and the EAN-2/5 add-ons; Code 128 in all three sets with shifts and FNC1 (GS1-128); Code 39; ITF and ITF-14; check digits for EAN/GTIN/SSCC/GLN, Luhn/IMEI, ISBN-10 and 13, Code 128 mod 103 and Code 39 mod 43; GS1 element-string building; QR through the EXISTING `core/qr.ts` (byte mode, levels L and M, versions 1 to 40).

**Suites (assertions / mutations killed).** `barcode` 77,309 / 169, `barcode-render` 15,516 / 54, `barcode-oracle` 1,327 / 36. Total 94,152 assertions, 259 mutations. All 107 Code 128 values; the Appendix V vectors (IMEI Code 128: `105 49 1 54 20 32 37 51 100 24`, check 93); module strings re-checked against the recorded independent-decoder verdicts; a 15,000-check pin that `check.ts`'s Luhn equals `unitKey.js`'s.

**Deviations.**
1. QR: no new encoder. Spec 13.4 keeps `core/qr.ts` as it is and does not build a GS1 QR at level Q; `qrsym.ts` only wraps it (4-module quiet zone, size, text cap, lone-surrogate refusal). The task text listed numeric and alphanumeric modes and more levels: following the spec, those are a separate decision (they would need their own tables-and-decoder test).
2. Data Matrix (T-6d) was skipped (an optional separate slice; owner question 10: write it, or load bwip-js lazily).
3. `buildGs1` and the GS1-128 symbol are in `gs1build.ts`, not `gs1.ts` as the 13.4 table has it, because T-5a owns `gs1.ts` (`parseGs1`). The two AI tables are duplicated; the `gs1` suite pins that they agree and that a string built in one parses in the other.
4. Code 128 set choice is the fewest-symbols dynamic programme (ties: fewest set changes, then earliest Set C), not the spec's literal "Set C for 4 or more digits". It is never longer (asserted against an independent rule implementation and an exhaustive search).
5. `check.ts` holds its own Luhn rather than re-exporting from `unitId.ts` as the 13.4 table says; pinned equal (above). `check.ts` throws on bad input where `unitKey.js` returns null.
6. `encodeItf14` refuses `wide: 2` and always draws a 3-module wide bar (GS1's range is 2.25:1 to 3:1); plain `encodeItf` takes 2 or 3. ITF-14 bearer bars are not drawn (a layout matter): the sources read give the 2 x X thickness but not the sideways extent, so no geometry was invented.
7. The GS1-128 data limit is 48 characters counting every separator (strict; see owner question 30). A GS1 field fed one digit too few is refused (the encoder would otherwise COMPUTE a check digit, and the bars would carry a different, valid-looking code than the one stored).

### T-6b: the label model and engine (lane P + M; all new files)

**Files.** `src/labelTypes.ts` (the types, in a new file, NOT `trackTypes.ts`, to avoid editing a shared file; `MrpField` gained an optional `src`); `src/core/labelModel.ts` (the template model and strict validators); `src/core/labelLayout.ts` (real-dpi dots, GS1 minimums, legibility floors); `src/core/labelRender.ts` (`fillRect` and `orMask` are exported so a suite can count writes: two exports beyond the spec's API); `src/core/labelRules.ts` (Legal Metrology Table-I and the FSSAI and Drugs Rules rows as data, cap-height measurement from the bundled IBM Plex files); `src/core/labelTemplates.ts` (the 14 library templates as data); `src/core/labelJob.ts` (the multi-label raw job and the four-label calibration drawing); `electron/labelLang.cjs` (the TSPL emitter, pure CJS); `scripts/assert/label.oracle.mjs` and `label.record.json` (recorded Apple Vision readings of the rendered labels).

**Suites (assertions / mutations killed).** `labelengine` 1,617 / 231, `templates` 533 / 335, `labelmodel` 394 / 106, `labelrules` 383 / 172, `labeljob` 214 / 127, `labellang` 158 / 82. Total 3,299 assertions, 1,053 mutations. (The builder's own report, before the review fixes, said 3,171 assertions and 992 mutations.) Dot alignment, GS1 minimums and legibility floors, the four-label calibration drawing, a differential test that the CJS twin of the validator in `labelLang.cjs` agrees reason by reason with `labelJob.ts`.

**Deviations and judgement calls.**
1. TSPL ONLY. ZPL is refused with the reason "zpl is not enabled: its graphic-field command has not been read or proven on a printer". The TSPL polarity (a 0 bit prints) is read from the TSC manual's figure and is unproven on hardware. The manual's pages 68 and 69 sample bytes differ in one byte; the suite pins which was used. The printer's own mm-to-dots truncation (8, 12 and 24 dots per mm) is an unproven risk. The TSPL `DIRECTION` is stored in the printer's memory (spec 13.6, T-6s): the printer profile will carry it (default 1) when T-6c is built.
2. Legal Metrology Table-I boundaries are inclusive at the UPPER bound, so a boundary value (exactly 50, 100, 500 or 2,500 cm2) belongs to the LOWER band. The spec's first text applied the larger band (read from extracted text that had lost its inequality signs); the build and review read the rendered pages and the spec has been corrected in this commit (sections 13.8, 18 item 7 and Appendix V). The numeral ratio 0.698 was measured from the bundled IBM Plex files.
3. Rule 7(4) is an exemption and 7(5) an area rule (the spec's reading was corrected from the source). The FSSAI rows are read from Version-V (13 October 2022), where 8(1)(a) also covers the expiry; later amendments were not read. The shelf-life boundary is 92 days. FSSAI and Drugs Rules rows are warnings only, and no code path says "compliant".
4. MRP wording: "MRP", the rupees and the amount, and in the full form "incl. of all taxes" are THIS APP'S OWN fixed wording, not prescribed text (the Rules' abbreviated illustrations are struck out of the consolidated book by GSR 779(E)). Owner question 29 asks whether to offer the spelled-out form.
5. Legibility floors are in millimetres, independent of dpi. The narrowest bar was a floor of 2 DOTS at every dpi (0.250 mm at 203 dpi, 0.169 mm at 300, 0.085 mm at 600): after the review it is judged in millimetres. `MIN_BAR_HEIGHT_MM` is 5 mm [J] (owner question 30). GS1 trade barcodes use `gs1MinModuleDots = ceil(0.264 mm x dpi / 25.4)`, with bars of at least 18.28 mm; the `prepack-60x40` template deliberately warns "below the GS1 minimum" because the bars cannot reach 18.28 mm in 40 mm.
6. A code or its human-readable text longer than 200 characters is refused with `barcode-invalid`. A code a label's text cleaning would change (a leading, trailing or doubled space, a tab or a hidden character) is refused rather than repaired: a repaired code would be a different code from the one stored.
7. The test label is four labels (ruler and frame, EAN-13, Code 128, QR) rather than one. The 25 x 15 jewellery variant and a Data Matrix drawing are not built. Label rotation is not modelled.
8. `labelLang.cjs` carries a hand-written CJS twin of `labelJob.ts`'s validator (a renderer cannot `require` CJS). T-7a's bridge should reuse it, not rewrite it. The `templates` suite has an "inertness" check (the library touches no app file) that T-6c and T-7a must update when they wire the library in.

## 3. The review and fix pass (what changed after `914fa39`)

A review pass, then two fixer reports. **The reports as relayed to this note were cut off mid-text, so the per-finding lists are not reproduced here; what follows is what the first sentences of the reports say and what the diff against `914fa39` shows.** The two fixers reported 15 and 22 confirmed findings, "fixed at the root" with failing-before assertions and updated mutation lists, except two minor items in the first report (and two open items it disclosed) and two items left unchanged on purpose in the second (documented in the code). Which items those are is NOT restated here: read the comments in the diff (`git diff 914fa39 -- src backend electron`) before relying on any one of them.

Verifiable from the diff (52 files, 2,678 insertions, 462 deletions, none outside the slices' own files except the spec):
- **Scanning.** The learned `gapMs` uses the 95th percentile of the pooled gaps and is clamped to 15 to 60 ms (it was the 99th and 120): with 400 pooled gaps the 99th is the maximum, one 60 ms gap taught 120 ms, and a person typing `7000` then Enter at 110 ms a key read as a scan and lost the Enter. A person's own value may still go to 120 (the setup screen warns above 60). A burst that stalls and resumes is never read as two scans (a cut-short run is remembered for 1 s if scanner-shaped, 300 ms otherwise, and what follows is discarded with its terminator); a Tab is never swallowed (with `tabIsGs` on, any Tab within 3 x `gapMs` of a printable key was lost); `none` as a terminator is written only when the person confirms it; the resolver treats a GTIN held ONLY as a retired code as such (it used to say "no such item", which hid the item from the Data Check and prompt).
- **Rules and cost.** Stored overrides cover a finding only when they could have been given at all (`overrideCovers`: a real reason, the same rule, line and unit, a right somebody may give, and for a negative cell at least the shortfall); the voucher as stored is judged by the same rules first so an edit is not blamed for what it did not make (a back-dated sale or receipt carries its own finding); two indexes replaced a scan of every voucher per line (`countsAt`, `batchSales`: 1,000 batch count lines against 50,000 vouchers took 521 ms of CPU before; `trackindex` proves the answers equal an independent brute-force scan and that vouchers are walked a constant number of times). Two cost defects are named in the code comments and the first fixer's report: a 5,000-row purchase against a 100,000-unit history took 26 s (the comment's figure; the fixer's run of the new suite against the old sources took 56 s of CPU), and the adoption path cost O(pieces log pieces) per adoption (6,000 unknown IMEIs sold against 6,000 one-unit purchases). The comments say what replaced them; the new suites time both with wide CPU bounds.
- **Labels.** The Table-I boundary correction, the MRP wording note, the millimetre bar floor, the 48-character GS1-128 count, "printed as stored or not at all", and `gapXMm` in the roll layout (the gap between the columns was left out, counted as 0, so a 2-up roll of 38 mm labels with 3 mm between them was told 76 mm).
- **Spec.** `docs/design/batch-serial-labels-spec.md` is the only existing file this branch edits: the Table-I boundary reading (sections 13.8, 18 item 7, Appendix V); the scanner's learned-gap rule and the stall and two-scan rule (14.2); the TSC `DIRECTION` note in T-6s; owner questions 29 and 30.
